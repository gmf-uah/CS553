# Part 1 Conceptual Foundations

## 1. Authentication vs. Authorization

- What is the difference between them?

    - **Authentication is when a user successfully logs in to a remote server, receiving a token in response that is the server's way of telling the client "you are who you say you are."**

    - **Authorization is a conditional state following authentication where, while the user may have successfully logged in, they still need certain permissions to complete an action. For example, an authenticated user may try to delete other users but not be authorized to do so without an admin role.**

- Describe what an API should return in each of the following situations:

    - The request does not contain valid authentication credentials.

        - **401 Unauthorized. This seems counterintuitive because we just got done saying this situation is about authentication, and that they mean different things; however, this is an unfortunate legacy holdover from before the distinction was standarized.**
    
    - The caller is authenticated but does not have permission to perform the requested operation.

        - **403 Forbidden**
    
    - **In both situations, the client request is rejected.**

## 2. Passwords, Sessions, and Tokens

Explain:

- why the application should never store passwords as plain text,

    - **If passwords are stored as plain text, then one database leak by a bad actor, internal or external, compromises all user login information. This would effectively allow anyone with that database access the ability to log in as any user and send requests to the server on their behalf, e.g. sending money in a banking app.**

- what the server should store instead,

    - **While in a non-HTTPS protocol the server may receive plaintext passwords across a connection, it is the server's job to 'hash' the password. This is a destructive process for which the original input is unrecoverable, so there is no risk of a hacker just finding where the cryptographic cipher is to undo the 'encryption' process. However, every input (password) when hashed will yield the same output, so when a user attempts to logs in, it succeeds only if the hashes match.**

- how a session-based login differs from a token-based login,

    - **Token-based logins do not store any data associated with a user's login session. When a user requests an authenticated action, the server doesn't check to see if that user is logged in using an in-memory table or a database, but rather takes the token in the request's header and decrypts it to read information about the user.**

    - **Session-based logins use a random string (UUID) generated by the server and associated with any user who successfully logs in. The string is stored in memory or a database, and is checked every time a user performs any action that requires authentication.**

- one advantage of each approach.

    - **Token-based logins don't require any of these tradeoffs associated with session-based logins, as no data is stored pertaining to a user's login state.**
    
        - **Each user's login session is effectively declarative, meaning that a token's validity is determined entirely by the contents of the token sent by the client rather than by comparing it against data on the server.**

        - **By contrast, when using sessions, with 5 servers supporting a website there will either be database query overhead (ping time, API usage) associated with needing a single source of truth, OR there will be engineering overhead associated with ensuring every server instance has synchronized session IDs.**

    - **Session-based logins are the 'obvious' solution, and they don't have the downside token-based logins have where tokens can't be revoked. If a user accidentally leaks their password and contacts support to automatically log out all instances of their account, session-based logins easily allow site staff to revoke access until the password is changed.**

## 3. JSON Web Tokens

Describe the purpose and structure of a JSON Web Token (JWT).

**JSON Web Tokens allow requests sent by a client to only be performed by the server if it is verified that the client is associated with the user the server performs the request for.**

**The token is split into header, payload, and signature. The header contains what algorithm is used to tell the server what encryption algorithm is used to decode the signature, while the signature itself tells the server that the other data in the JWT hasn't been tampered with e.g. changing the user's role from `Guest` to `Admin`, or changing the token's expiration time.**

**The payload contains the data the user is sending to the server, e.g. submitting a search query on Amazon.**

**Without validating the JWT, the server could perform actions like deleting other users based on requests sent by a random user who is faking that they have an `Admin` role.**

**JWTs are designed to expire after a certain period of time for security purposes. If a user's JWT is leaked, then an attacker can use that to perform requests on their behalf; if the expiration time is too long, then the attacker can impersonate the user indefinitely.**

## 4. OAuth

Explain the purpose of OAuth.

**OAuth allows websites to delegate their authorization needs to third-party services like Google (Sign in with Google) with which the user likely already has an account. It removes the burden of engineering secure and robust account security from the website's developers, allowing users to interact with website APIs.**

**If the user (the resource owner) opens an app (client application) on their phone and it prompts the user to share their location, then OAuth is what allows the app to access that location after the user allows it.**

**Perhaps the user signed into that app with Google. Then Google is the authorization server that gives the client application an access token (faux password, basically 'scrimp') to get the location data from the resource server.**

**It is safer for the authorization server to give the client application an access token rather than a password because there is then no chance that the password can be leaked or decrypted by the client application or resource server, as only Google has the password information. If the access token is leaked, then in the above example, all an attacker could do is access the user's location data.**

## 5. PKI and Certificates

Explain how a digital certificate helps a client establish a secure connection to an API server.

**Digital certificates are used by servers for clients to be able to trust that the server they are sending a request to is the real one expected to be associated with that address. A certificate authority (CA) is an entity, usually an organization, that is agreed upon by most server hosters (especially the most-used ones) to be a trustworthy party. Those CAs are the ones that grant digital certificates that let clients know a server is the one they are indeed the one they intend to visit.**

**Such certificates are encrypted with public keys owned by the server, and signed with private keys owned by the CA. The client then cross references that public key with the certificate's public key, confirming the CA granted the digital certificate to the server.**

**If there was no certificate validation, then the client could visit a website they thought was `google.com`, with that exact address, but it's the wrong server, spoofing that address. The user might then try to log in and submit their actual `google.com` password credentials, thus giving the fake server access to their account.**

## 6. Databases, Messages, and Asynchronous Processing

An API receives a request to generate a large report. Producing the report may take several minutes.

Explain why the API should normally use asynchronous processing instead of keeping the HTTP request open.

**If the HTTP request is kept open while producing the report, then the server will be unreachable during the entire production time. Any pages clients attempt to visit will not load until the report is produced and returned to the requesting user.**

**A reasonable API design for a server-side task might take a significant amount of time to complete is one that is executed asynchronously. Such a task is delegated to a background worker, which could either work on its own CPU core or in a different thread. When a client submits a request that gets delegated this way, the server returns a 202 status code ("Accepted") which indicates the process is ongoing. To return a response to the client when the job finishes, the client 'subscribes' to the server so that when it 'publishes' a message saying the job finished, the client will receive the data it asked for initially.**

**If multiple jobs are scheduled, having them all occur asynchronously could crowd out server resources. A threshold for 'maximum jobs running at one time', when met, causes the server to place further jobs into a message queue, to begin only once the current jobs have completed.**

## 2. Database and Asynchronous Behavior

Why should the task ID be supplied as a query parameter instead of being inserted directly into the SQL string?

- **SQL injection is an insecurity caused by an attacker placing SQL commands into a request payload in the hope that the server inserts it to the database query, allowing them arbitrary access to the database to do things like retrieving unauthorized data or deleting data. When the task ID is supplied as a query parameter to the database query, the ID isn't considered as part of the query instruction but rather as data, so no SQL injection can occur.**

Why must the route use `await` when calling `db.query()`?

- **`db.query` is an asynchronous function, meaning it returns a `Promise` immediately rather than waiting until the database has finished its query to return the result of the function call. `await` just goes ahead and waits for that result, which comes through the completed `Promise`.**

## 1. Following a Request Through the System

Choose one protected API operation and trace it from the client’s request to the server’s response. Identify one place where the request could fail and explain how the API should respond.

**When a client wants to retrieve one of their tasks through the `GET /tasks/:id` route, they make an HTTP request - a TCP message following a particular format that also expects a response message. Express, a JavaScript framework, is built around organizing HTTP requests like `/tasks/:id` into function calls with request and response objects that give the developer easy access to features of HTTP.**

**Once the server receives the HTTP request, it first verifies that the client is the user that they say they are by authenticating that the token in the request header has a payload matching the user's token at their login time. From there, a database call is made by the server to fetch the task the user wants, but the server only returns that task to the user if the task's owner is also the user; otherwise, the request fails authorization, returning status code 403 Forbidden.**

## 2. Synchronous vs. Asynchronous Processing

Describe one operation that should be completed directly in an HTTP request and one operation that would be better handled using a message queue and background worker.

**Operations that doesn't require database calls or significant computations are ones that can be performed synchronously without fear of causing the server to hang on a request that depends on such an operation. For example, a `GET /health` check has no need to ever be defined asynchronously; the client is receiving what amounts to a ping response from the server.**

**An asynchronous operation is one that the developer anticipates taking long enough that it's unreasonable to expect a user to wait for the operation to complete before initiating other requests. An example of an  operation best handled asynchronously is SymboLab's integral solver, which can often take upwards of 30 seconds to produce a result. Without asynchronous execution, those 30 seconds of stalling would cause the site to effectively freeze for all users.**

**If an asynchronous task fails, the client's subscription to the topic receives a publish event from the server saying as much. How the client responds to the failure is contextual, but likely a status bar or notification would indicate so.**

**A database could be used as a single source of truth to determine if a previously scheduled operation has been completed. For example, if a client submitted a request for a report to be generated (as per this repo's example), and requested an update after 30 minutes of waiting, then the server would need to consult a central database that is regularly updated with operational progress. Without that central database, every server instance's memory could have a different operational progession report, so that database is important.**
